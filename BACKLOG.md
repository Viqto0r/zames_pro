# BACKLOG — идеи по улучшению zames_pro

Документ ведёт сам агент (self-review). Здесь копятся находки, идеи и
технический долг, которые НЕ являются блокерами, но стоят внимания.
Формат: заголовок → суть проблемы → почему важно → как чинить (набросок).

Приоритеты: **P0** — баг/риск потери данных, **P1** — заметная боль,
**P2** — качество/поддерживаемость, **P3** — приятный бонус.

## P0 — Баги и риски потери данных

### 1. `require()` в ESM-модуле: `windowsReachable()` и `resolveSrcDir()` молча ломаются

В `src/attachments.ts:270` и `src/self-review.ts:20` используется
`require('fs')`, хотя проект — чистый ESM (`"type": "module"`). В ESM
`require` не определён: `typeof require === 'undefined'`, а вызов бросает
`ReferenceError: require is not defined`.

Проверено вживую (`node tmp/probe.mjs` и запуск через `tsx`): вызов падает.

Последствия:

- `windowsReachable()` → `try/catch` глотает `ReferenceError` и всегда
  возвращает `false`. Значит `isWsl()` в реальном WSL тоже вернёт `false`,
  и **чтение картинки/файлов из Windows-буфера в WSL не работает вообще** —
  ровно та функция, ради которой этот код и написан.
- `resolveSrcDir()` (self-review) → цикл по кандидатам всегда падает на
  `require`, поэтому возвращается `__dirname`. При запуске из `dist/` там
  нет `.ts`-файлов → `copyDirJsFiles` копирует 0 файлов → `/self-review`
  падает с `self.no_src_err`. В dev (tsx из `src/`) случайно работает,
  потому что `__dirname` — это `src`. То есть **опубликованный билд
  self-review нерабочий**, а в dev это не заметно.

Как чинить: заменить `require('fs')` на обычный импорт `import fs from 'node:fs'`
(`fs` уже импортирован в обоих модулях — переиспользовать), либо
`createRequire(import.meta.url)`. Для `resolveSrcDir()` дополнительно
сделать детект по `readdir` через импортированный `fs/promises`.
Добавить регресс-тест: `windowsReachable()` не должен бросать, и
`resolveSrcDir()` из dist-подобной директории находит `../src`.

### 2. Не-атомарная запись конфига и сессий

`writeConfigValue` / `resetConfigValue` (`src/config.ts`) и сохранение
сессии (`src/sessions.ts`) пишут через `fs.writeFileSync(file, ...)` прямо в
целевой файл. Если процесс упадёт/убьют в момент записи (а это CLI, где
Ctrl+C — обычное дело), `~/.zames/config.json` или файл сессии останется
битым/пустым, и агент стартует без настроек или теряет сессию.

Как чинить: писать во временный файл рядом (`<file>.tmp`) и `renameSync`
поверх целевого (rename атомарен в пределах ФС). Общий хелпер
`writeFileAtomic(path, data)` и перевести на него config, sessions, undo.

## P1 — Заметные улучшения

### 3. Хардкод русского в `config.ts`

`src/config.ts:483`: `throw new Error('не удалось прочитать ${file}: ...')`.
Это единственная русская прозаическая строка в модуле, который по политике
проекта (см. AGENTS.md «Language policy») должен быть agent-facing/EN либо
идти через i18n CATALOG. Сообщение утекает оператору при битом конфиге.

Как чинить: либо перевести на английский (как остальные ошибки ядра), либо
пропустить через CATALOG (ключ вида `config.read_failed`).

### 4. Неиспользуемая зависимость `marked`

Аудит `package.json` показал: `marked` не импортируется ни в `src/`, ни в
`test/`, ни в `scripts/` (Markdown рендерит `markdansi`, который тянет
свой парсер). Лишняя зависимость в проде = лишний вес, поверхность
обновлений и потенциальные CVE.

Как чинить: удалить `marked` из `dependencies` (`npm rm marked`), прогнать
`npm run build` и тесты.

### 5. CI ставит зависимости через `npm install`, а не `npm ci`

`.github/workflows/test.yml` и `publish.yml` используют
`npm install --no-audit --no-fund`. При наличии `package-lock.json`
правильнее `npm ci`: воспроизводимая сборка строго по локфайлу, быстрее,
падает при расхождении lock/package.

Как чинить: заменить на `npm ci --no-audit --no-fund` в обоих workflow.

### 6. Нет `CHANGELOG.md`

Версии бампаются вручную (`chore: bump version to X`), но истории изменений
для пользователя нет. Для CLI, который часто релизится, это заметная боль:
непонятно, что нового между версиями.

Как чинить: завести `CHANGELOG.md` (keep-a-changelog) и/или генерировать
его из git-тегов в `prepublishOnly`. Достаточно начать вести с текущей
версии.

## P2 — Качество и поддерживаемость

### 7. Монолитные модули

`src/index.ts` — 3843 строки, `src/browser.ts` — 3337,
`src/input.ts` — 2179. Логика вперемешку: CLI-диспетчер, runTask, очередь,
рендер статуса, команды. Это затрудняет и точечные правки, и само-ревью
(чем больше файл, тем дороже читать его модели).

Как чинить (постепенно, не разом):
- вынести `runTask`/очередь/планировщик-тикер из `index.ts` в
  `src/run-task.ts`;
- вынести слэш-команды, которые сейчас в `index.ts`, в отдельный
  `src/commands-runner.ts` (чистые части уже в `commands.ts`);
- в `input.ts` отделить модель буфера от рендера/парсинга клавиш.

Осторожно: `index.ts` почти не покрыт юнит-тестами, поэтому рефакторинг
только под защитой уже существующих тестов + ручной смоук.

### 8. Тест i18n проверяет только выборку ключей

`test/i18n.test.ts` проверяет наличие ru/en лишь для ~11 ключей. Полнота
каталога (у каждого ключа есть и ru, и en) не гарантируется — легко
добавить ключ только на одном языке, и тест это не поймает.

Как чинить: экспортировать `CATALOG` из `i18n.ts` и в тесте пройтись по
ВСЕМ ключам, проверяя наличие обеих локалей и непустые строки. Это
дёшево и убирает целый класс регрессий.

### 9. [x] Нет измерения покрытия — сделано в 950c7ee

522 теста — это хорошо, но непонятно, какие модули не покрыты (а монолиты
из п.7 точно не покрыты). Добавить `c8`/`node --experimental-test-coverage`
и публиковать отчёт (хотя бы в артефакты CI), чтобы видеть дыры.

### 10. `AGENTS.md` разросся до ~70 КБ

Файл загружается в контекст задачи через `loadProjectContext` и стоит
токенов на каждом запуске. Часть разделов — историческая (почему были
баги X) и уже не нужна модели в каждой задаче.

Как чинить: вынести исторические «почему так» в `docs/DESIGN-NOTES.md`,
а в `AGENTS.md` оставить только действующие правила и краткие ссылки.
Заодно проверить, что `AGENTS.md` не дублирует README.

### 11. Нет `.nvmrc` / `packageManager`

`engines.node >= 20`, CI на Node 24, локально — 24. Разброс версий грозит
«зелёными у меня» тестами (в AGENTS.md даже описано, что Node 22
отменяет тесты из-за unref-таймеров).

Как чинить: добавить `.nvmrc` с 24 и, при желании, поле `packageManager`
(`npm@...`), чтобы версии были зафиксированы явно.

## P3 — Полезные мелочи

### 12. `/self-review` умеет только `.ts`

`copyDirJsFiles` копирует лишь `*.ts` из `SRC_DIR`. После фикса п.1 это
будет работать, но снапшот не включает `scripts/`, `eslint.config.js`,
`tsconfig*.json` и т.п., хотя ревью часто их касается.

Как чинить: сделать список расширений/файлов настраиваемым и включать
хотя бы `scripts/**` и конфиги.

### 13. [x] `self-smoke` задокументирован в CONTRIBUTING.md (в CI не гоняем: нужны креды) — 950c7ee

`npm run self-smoke` — единственный end-to-end прогон (реальный браузер,
логин, инструменты, вложения). В CI он отсутствует (нужны креды и сеть —
поэтому и не включён). Стоит хотя бы задокументировать ручной прогон
перед релизом в `CONTRIBUTING.md` или добавить опциональный
`workflow_dispatch`-job.

### 14. [x] Добавлены CONTRIBUTING.md и SECURITY.md — 950c7ee

Для публичного npm-пакета полезно иметь короткий гайд по локальной
разработке (какие команды, как запускать тесты/линт/смоук) и политику
безопасности. Сейчас всё это размазано по AGENTS.md (для агента) и README
(для пользователя).

### 15. [x] WebFetch: SSRF-гард + ретраи — 950c7ee

`httpFetch` (`src/web.ts`) не фильтрует приватные диапазоны/`localhost`
и не делает ретраев на 5xx/таймаут, хотя это частый случай при скрейпинге.

Как чинить: блокировать запросы к приватным IP/hostname и добавить
1–2 ретрая с экспоненциальной паузой на сетевые ошибки/5xx.

## Как пользоваться этим файлом

- Пункты не удалять по мере выполнения, а помечать `[x]` и датой — так
  видно, что уже сделано.

  файл на каждую.
