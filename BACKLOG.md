# BACKLOG — идеи по улучшению zames_pro

Документ ведёт сам агент (self-review). Здесь копятся находки, идеи и
технический долг, которые НЕ являются блокерами, но стоят внимания.
Формат: заголовок → суть → почему важно → как чинить (набросок).

Приоритеты: **P0** — баг/риск потери данных, **P1** — заметная боль,
**P2** — качество/поддерживаемость, **P3** — приятный бонус.

> Контекст: код проекта не читают люди — агент модернизирует сам себя.
> Поэтому приоритет у того, что (а) вводит в заблуждение САМОГО агента
> (AGENTS.md/SECURITY.md идут в контекст каждой задачи), (б) снижает цену
> само-правок (размер модулей, тесты, детерминизм), (в) даёт агенту новые
> рычаги самоулучшения (план-режим, хуки, чекпойнты, /improve).

## P0 — Баги и риски потери данных

### A1. `atomicWriteJson` в config.ts — общий хелпер продублирован, undo/sessions всё ещё пишут не везде атомарно

`config.ts` уже пишет через temp+rename, undo/sessions тоже переведены
(2.53.1). Но:

- нет ОДНОГО экспортируемого `writeFileAtomic(path, data)` — логика
  temp+rename продублирована минимум в `config.ts` и `undo.ts`;
- transcript (`transcript.ts`) пишет в append-стрим без fsync — при
  жёстком kill последняя строка JSONL может оказаться битой; `/export`
  и `/cost` парсят transcript (`parseTranscript`) и на битой строке могут
  упасть или молча потерять хвост.

Почему важно: CLI, где Ctrl+C — норма, не должен терять историю и сессии.

Как чинить: вынести `writeFileAtomic()` в `src/fsutil.ts`, перевести на
него config/sessions/undo. `parseTranscript` сделать устойчивым к битой
последней строке (skip-and-warn вместо throw).

### A2. Устаревшие ссылки на удалённую подсистему подтверждений (confirm / /permissions)

Подсистема подтверждений удалена в 2.55.0 (мёртвый код), но ссылки на неё
остались и ВРУТ:

- `SECURITY.md:23-24` — «Confirmation prompts … the `alwaysConfirm` regex
  list … Review them in `/permissions`» — команды `/permissions` и ключей
  `alwaysConfirm` больше НЕТ. Это ложное обещание защиты в политике
  безопасности публичного пакета.
- `AGENTS.md` — в списке команд всё ещё есть `/permissions`, в карте
  модулей упоминается `confirm.ts`, в разделе Configuration — секция
  `confirmation` и примеры `confirmation.write`.

Почему важно: AGENTS.md инжектится в системный промпт КАЖДОЙ задачи — агент
читает несуществующие правила, а `SECURITY.md` обещает оператору защиту,
которой нет. Это ещё и токены в каждом запуске.

Как чинить: вычистить упоминания `confirm`/`/permissions`/`alwaysConfirm`
из AGENTS.md и SECURITY.md; в SECURITY.md честно написать, что сейчас
подтверждений нет (или описать реальный план их возврата, см. C1).

### A3. `gitTools.ts` GitPush может потерять вывод при интерактивной аутентификации

`runGit` ставит `GIT_TERMINAL_PROMPT: '0'` (правильно), но `GitPush`
строит команду конкатенацией: `git push ${flag} origin ${branch}` с
`quoteArgs` (JSON.stringify) только для отдельных полей. Ветка/remote
из аргументов модели не валидируются. Стоит явно требовать валидное имя
ветки (regex) — иначе риск инъекции в shell.

Почему важно: ветка/remote приходит от модели; через них можно подсунуть
`; rm -rf`.

Как чинить: валидировать `branch`/`remote` регуляркой
`^[\w./-]+$`, отклонять всё остальное до запуска git.

## P1 — Заметные улучшения

### B1. Plan mode / read-only режим (идея Claude Code)

Сейчас любой запуск агента сразу МОЖЕТ писать. У Claude Code есть plan
mode (read-only исследование + предложение плана без правок), у Codex —
sandbox/approval.

Почему важно для self-improvement: агент часто должен сначала ИЗУЧИТЬ
код (прочитать 10 файлов), а потом уже править. Двухфазный режим снижает
риск «полез в правки, не разобравшись» и экономит дорогой проход
write+undo при ошибке.

Как чинить: флаг `--plan` и команда `/plan`; в этом режиме набор
инструментов = только чтение (Read/Glob/Grep/LS/GitStatus/GitDiff/GitLog),
Write/Edit/Bash/MultiEdit/ApplyPatch исключаются из `createTools()`. По
команде `/go` (или ответом оператора) — переход к обычному режиму с
сохранением накопленного анализа. Минимум: гейтить записывающие тулы на
уровне `createTools({ readOnly: true })`.

### B2. Hooks PreToolUse / PostToolUse (идея Claude Code)

Нет способа повесить на событие внешний скрипт: например, авто-`prettier`
после каждого Edit или блокировку `Bash` с `rm -rf`.

Почему важно: это расширяемость без правки ядра — оператор (и сам агент)
может настроить политику под проект в `.zames/hooks.json`.

Как чинить: `src/hooks.ts`; конфиг
`{ "PreToolUse": [{matcher, command}], "PostToolUse": [...] }`;
в `agent-loop.ts` перед `tool.fn` дёргать PreToolUse (выход != 0 → отказ,
stderr идёт в tool-result), после — PostToolUse (stdout как
дополнение к результату). Best-effort, ошибка хука не валит цикл.

### B3. Чекпойнты / rewind (идея Claude Code)

Undo уже есть (пофайловый), но нет «откатить всю задачу разом».

Почему важно: после рискованной задачи хочется вернуться к состоянию
«до» одной командой, а не `git stash` вручную.

Как чинить: снимать git-снимок (или tarball) в начале каждой задачи в
`~/.zames/checkpoints/<stamp>/`, команда `/rewind [n]` — вернуть рабочее
дерево к снимку (с подтверждением и backup). Опирается на существующий
`undo.ts` и `self-review` snapshots.

### B4. `--output-format json` / headless-режим для скриптов (идея Codex)

Сейчас вывод — человекочитаемый текст с цветом и спиннером. Для CI/скриптов
нужен машиночитаемый поток событий.

Почему важно: позволяет встраивать zames в пайплайны и автотесты, а самому
агенту — вызывать zames как инструмент.

Как чинить: флаг `--output-format <text|json|jsonl>`; в jsonl писать те же
события, что уже идут в `transcript.log` (tool_call/tool_result/answer/
final). Транскрипт уже есть — останется прокинуть его в stdout и заглушить
UI. Это дёшево, т.к. `Transcript.log` уже покрывает почти всё.

### B5. `@file`-ссылки в промпте (идея Claude Code)

Оператор не может быстро подсунуть файл в задачу: надо либо вложение, либо
просить агента прочитать.

Почему важно: `реши задачу @src/browser.ts` удобнее и дешевле, чем «прочитай
файл …» отдельным ходом.

Как чинить: в `expandPastes`/обработке сабмита распознавать токены
`@path` (через существующий `path-token.ts`/`looksLikeFilePath`),
инлайнить содержимое в начало задачи (с ограничением размера) или
превращать в attachment-marker.

### B6. Path-scoped правила (идея Claude Code conditional rules)

AGENTS.md один на весь проект. Нет «правил для конкретной папки».

Как чинить: поддержать frontmatter `paths: ["src/**"]` в AGENTS.md или
отдельные `AGENTS.md` в подпапках (частично уже есть — загрузка идёт по
цепочке вверх, но НЕ вниз в подпапки). Расширить `loadProjectContext`,
чтобы при задаче, затрагивающей файлы, подтягивались ближайшие вложенные
инструкции. Снижает раздувание корневого AGENTS.md (см. C2).

### B7. Кастомные команды: аргументы и автодополнение

Свои `.md`-команды поддерживают `$ARGUMENTS`/`{{args}}`, но в подсказке «/»
не видно их аргументов, и нет валидации обязательных.

Как чинить: frontmatter `argument-hint` / `arguments:` (как в Claude Code),
показывать подсказку в suggest-листе, подставлять позиционные `$1 $2`.

## P2 — Качество и поддерживаемость

### C1. Вернуть подтверждения правильно (в agent-loop, а не декоративно)

Подсистему удалили, потому что она не была подключена. Но сама идея
approval-policy полезна (Codex/Claude Code её имеют).

Как чинить: реализовать в `agent-loop.ts` РЕАЛЬНО: перед выполнением
мутирующего тула проверять политику (`ask`/`allow`/`deny` по regex на
команду/путь), при `ask` — читать ответ оператора из input. Политику — в
`.zames/permissions.json`. Не «включать конфигом» мёртвый код, а сделать
рабочим с самого начала.

### C2. `AGENTS.md` разросся (~70 КБ) и грузится в каждую задачу

Включая исторические «почему был баг X», которые модели в каждой задаче
не нужны.

Как чинить: вынести историю багфиксов в `docs/DESIGN-NOTES.md`, в
AGENTS.md оставить действующие правила + ссылки. Разбить по темам
(`docs/*.md`), грузить их по требованию через `/context`-подобный механизм
(progressive disclosure, как skills). Это прямая экономия токенов и
уменьшение шума в промпте.

### C3. Монолитные модули (index/browser/input/agent-loop/i18n)

`index.ts` ~4037 строк, `browser.ts` ~3337, `input.ts` ~2184,
`agent-loop.ts` ~1728, `i18n.ts` ~1637. Рефакторинг под защитой тестов.

Как чинить (постепенно):

- `runTask`/очередь/планировщик-тикер → `src/run-task.ts`;
- слэш-команды из `index.ts` → `src/commands-runner.ts` (чистые части уже
  в `commands.ts`);
- в `input.ts` отделить модель буфера от рендера/парсинга клавиш;
- в `i18n.ts` разбить CATALOG по секциям (help/config/prompt/...) на файлы
  и собрать в один объект — сейчас это один гигантский литерал.

Осторожно: `index.ts` почти не покрыт тестами → только под защитой
существующих + ручной смоук.

### C4. Самоулучшение: команда `/improve` (BACKLOG-driven loop)

Есть BACKLOG.md, есть self-review, есть тесты — но нет команды, которая
берёт верхнюю невыполненную задачу из BACKLOG и ДОВОДИТ её до коммита.

Почему важно: это и есть суть «агент модернизирует сам себя». Замыкает
цикл: backlog → реализация → тест → changelog → commit.

Как чинить: `/improve [n|id]` — прочитать BACKLOG.md, взять P0/P1 (или
указанный id), отправить агенту задачу «реализуй пункт X, прогони
`npm run typecheck && npm test`, обнови CHANGELOG и BACKLOG (отметь [x]),
закоммить». Переиспользовать существующий `runTask`. По завершении —
пометка в BACKLOG автоматически (сейчас это делалось вручную в коммитах
`docs(backlog): mark ... done`).

### C5. Расширить coverage-gate

Сейчас floor только для нескольких «чистых» модулей. Дыры в монолитах
(P2/C3) невидимы.

Как чинить: добавить в `coverage-gate.mjs` минимальные пороги ещё для
нескольких модулей (net-capture, attachments, context, scheduler,
commands, xml-toolcall) и печатать топ-10 непокрытых файлов в логе CI,
чтобы регресс по покрытию был заметен.

### C6. Детерминизм версий MCP-серверов

Пример и README рекомендуют `npx -y @playwright/mcp@latest` — плавающая
версия. Сервер может обновиться и сломать поведение между запусками.

Как чинить: в README и при `/mcp` рекомендовать пиннинг версии; можно
предупреждать, если в конфиге `@latest`.

## P3 — Полезные мелочи

### D1. Streaming-вывод ответа

Ответ печатается только целиком (из `_netCapture`). Оператор ждёт молча.
Как чинить: по мере поступления SSE-фрагментов дёргать `onAnswerChunk` и
обновлять буфер над инпут-линией (уже есть инфраструктура printAbove/
статуса). Рискованно (перерисовка), но сильно улучшает восприятие.

### D2. Автогенерация CHANGELOG из Conventional Commits

Сейчас CHANGELOG ведётся вручную. Коммиты уже почти conventional
(`feat:`, `fix:`, `chore:`). Можно собирать Unreleased автоматически в
`prepublishOnly`/CI.

### D3. `/cost` — больше метрик

Сейчас: задачи, тул-коллы, длительность, токены. Добавить разбивку по
инструментам (топ по времени/частоте) — помогает агенту видеть, где он
тратит время (частые Read→Edit циклы и т.п.).

### D4. Умный выбор инструмента: Edit vs MultiEdit vs ApplyPatch

Описание тулов не подсказывает, когда что. Добавить в системный промпт
краткую эвристику («несколько правок в одном файле → MultiEdit; несколько
файлов → ApplyPatch») — уменьшит число неудачных одиночных Edit.

### D5. `/help` — группировка команд

Список уже длинный (40+). Сгруппировать по разделам (session, git, config,
self-review, mcp) — как в `/config`.

### D6. Защита от повторного tool-call с тем же аргументом (loop detection)

Если модель зациклилась, повторяя один и тот же Read/Bash, нет явного
детектора петель. Добавить счётчик идентичных вызовов подряд и nudge
после N повторов.

### D7. `Glob` без `path` ищет от workdir, но `include` для Grep не имеет glob-ограничения

Мелочь: привести `Grep.include` к тому же sandbox-поведению и поддержать
несколько include-паттернов.
